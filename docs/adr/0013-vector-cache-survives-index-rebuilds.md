# Vectors live in a content-addressed cache that survives index rebuilds

Embedding the user's Sources takes about three hours (`MeaningTimingTests`: ≈ 3.1 h of backfill, 2.2 h of it code). The File Index has one rule for its format: an index of another `FileIndexSchema.version` is dropped and read again, never migrated, because everything in it comes from the disk. Reading names and contents again takes minutes. While vectors were stored in the index (`segments.vec`), every schema bump also threw away the three hours, and the schema changes often while the app is being built.

**The vectors moved out, into `VectorCache.sqlite`, keyed by exactly what was embedded.** A key is 16 bytes of SHA-256 over the cache's fingerprint and a description of the input: a text's whole prompt (title included); a photo or screenshot as its file's SHA-256 and soft-token budget; a PDF page drawn as a picture as the file, the page and the render size; a video frame as the file, its start and every setting that decides which frame lands there; a window of sound as the file and its span. The meaning pass keys every input before it asks the helper: a hit never reaches the helper, a miss is embedded and kept. The index keeps only the key (`segments.vec_key`). The memory-mapped search matrix (`FileIndex.vectors`) is built from the keys and the cache and can always be rebuilt.

**The cache has its own format and its own rules.** One table from key to vector, a table of each key's last day of use, plus `meta`, versioned on its own (`VectorCache.version`) and kept trivial. It is cleared only when its fingerprint changes: the model revision, the prompt scheme, and `inputs`, the version of how the helper prepares a picture or a recording. "Remove Model and Vectors…" also clears it. Otherwise an entry goes only when the daily prune finds it unused for more than 30 days (see Consequences).

**This is not a migration.** The index is still dropped and read again from the disk; nothing in it is carried over or converted. What survives is a separate store whose entries depend only on their inputs, so they are true for any index that comes to have the same input again. The one-time bridge from schema 4 is the same idea run backwards: before a schema-4 index is dropped, its `segments.vec` is keyed the way the meaning pass would key it today and put in the cache (`VectorCache.seed(fromIndex:)`). This only happens under today's `MeaningPass.fingerprint`. Text keys come from the stored Passages and the file's name. Media keys hash the file if it still has the size and date it was embedded at; otherwise it is left to embed again. On the dev machine's index (10,324 vectors), everything was seeded in 2.8 s and nothing was stale.

## Considered Options

- **Migrate the index.** Rejected: it breaks the rule that the index is disposable and comes from the disk. Every schema change would need migration code written and tested against data that only exists on the user's Mac.
- **Keep re-embedding on every bump.** Rejected: three hours of a busy GPU each time, and search by meaning is worse until it finishes.
- **Keep the vectors only in the index, and avoid bumping.** Rejected: it makes every format change wait on the vectors, or turns it into a migration.
- **Keep `segments.vec` and add the cache beside it.** Rejected: that is a third copy of every vector, after the cache and the search matrix. On the dev machine's index it would have been 823 MB against 804 MB.
- **Key a frame or a rendered page by the hash of the image bytes sent.** That is closer to "what was sent", but a schema-4 index could not be seeded from it without rendering every page and decoding every video again. Keying by the file and its position lets seeding work from stored data plus one hash per file, and lets a cache hit skip rendering a page altogether.

## Consequences

- A schema bump costs the minutes of names and contents. The meaning pass then runs on cache hits; `VectorCacheTests` pins zero helper requests for unchanged content.
- The same input is embedded once, wherever it is: two copies of a note with the same name, a picture duplicated in another folder, a file moved between Sources. A Source removed and added again comes back from the cache. On the dev machine, 6.6% of the inputs were duplicates.
- Disk: a vector takes 1.67 KB in the cache (8 KB pages; 2.08 KB on 4 KB pages) instead of 1.9 KB in the index, plus a 16-byte key in the index. The search matrix is unchanged at 1.56 KB.
- Left alone, the cache would only grow. A changed or deleted file's entries stay, an edited text file leaves behind the chunks after the edit point, because chunk boundaries move, and a removed Source leaves all of its vectors. So it is pruned: an entry is used when it is written, found, or referenced by the index, and keeps that day (days since 1970, written only when it is not already today, in its own small table so stamping does not rewrite vector pages). About once a day, when the system finds it a good time (`NSBackgroundActivityScheduler`), the prune stamps every key the index references, then deletes every entry unused for more than 30 days. A month lets an undone edit or a file put back cost nothing.
- The prune runs only when the index is caught up: the Sources applied, every file in them read and embedded, and the index not made anew this session. An index being read again after a schema bump points to few of its vectors until it is through, and must never lose the ones it is about to find. Until then the run defers and the system tries again later. A file that never finishes its contents or its vectors holds the prune back; that fails safe.
- Space comes back with `VACUUM` once the entries pruned since the last one come to a tenth of those left. `incremental_vacuum` was measured and not used: entries die scattered across pages, and deleting 40% of 14,000 at random freed whole only 240 of the ~1,140 pages they took.
- Version 2 added the table of last days. A version-1 cache is brought over in place, every entry used on the day of the upgrade: one statement, so a cache already filled survives it whole, and none of its entries can go before 31 days later. A cache of any other version is dropped and made again.
- Invalidation is by construction. A different input is a different key, so an entry can go unused but is never wrong. The exceptions are what a key cannot see: the helper's input preparation (bump `inputs`), the model or prompt scheme (the fingerprint), and a media file that changes while the helper reads it (not kept: its size and date are checked after the step). A frame's key depends on its stored start being reproduced by the same decode; if it is not, that frame is a miss, never a wrong hit.
- One seeding case is inexact. A file renamed after it was embedded kept its vectors under schema 4, because a move keeps Passages. Its text vectors were made with the old name as their title and are seeded under the new name's key. This is limited to files renamed between embedding and the upgrade. Edit the file to have it embedded again.
- If the cache is emptied or deleted, the index notices: `meta.vector_cache` no longer matches `VectorCache.id`, so `enable()` drops the index's vectors and embeds again.
